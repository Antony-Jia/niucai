# Bot 工作地图：像素办公室与白板协作

日期：2026-10-29 · 状态：只读地图首版已实现（见文末“实现状态”），真实环境验收未完成

关联：[桌面端简化设计稿](desktop-simplification-design.md) · [轻量 Kernel 与 Bot 白板方案](kernel-lite-redesign.md)

本次只定义产品、视觉、交互和数据要求，不修改应用、交互原型或后端，不生成游戏素材。下文布局、动画、接口建议和验收指标均为拟议能力。

## 1. 一句话定位

**把正在工作的 Bot 变成像素办公室里的小角色，让用户看见谁在忙、通过白板交流了什么、哪里需要自己帮忙。**

这是一种有游戏观感的工作视图。任务、白板和执行状态仍由 Kernel 管理；人物位置、走路、打字和装饰只是表达这些状态的方式，不参与调度。

用户不需要操纵人物、学习游戏规则或维护办公室。默认不引入金币、经验、等级、饥饿、体力和挂机奖励，避免把工作变成养成负担。

## 2. 入口：沿用简化后的三项导航

主导航继续是“任务、文件、设备”，设置在底部。“地图”是任务页的另一种观察方式，与列表共享当前工作空间、任务筛选和待处理数量。

```text
任务
  今天想完成什么？      [开始任务]
  我的任务             [列表 | 地图]
    列表：按任务看进度
    地图：按助手看协作

任务详情 → 查看协作地图 → 地图聚焦本任务
```

- 首次使用默认列表；用户主动切换地图后，可在本机记住选择。
- 地图不代替任务输入、审批和成果详情。新建任务继续使用同一个入口。
- 地图顶栏保留“需要你处理 N 项任务”的入口；不让用户必须在场景里寻找闪光物。
- 工作空间范围为当前 Kernel，不能把不同连接的 Bot、卡片和事件混在一张地图。
- 任务范围默认“全部进行中”；可切换“某个任务”或“全部状态”。范围在标题旁始终可见。
- 按任务筛选时只展示有真实关联的 Bot、卡片和事件；独立卡片保留“未归属任务”分组，不按标题猜测关联。

## 3. 场景设计：一个温暖、安静的像素办公室

采用俯视偏斜视角的 2D 像素场景，浅米色地板、蓝灰工位、暖色灯光，与现有品牌蓝协调。目标是看起来像一间有人在工作的办公室，而不是增加一张技术拓扑图。

### 页面线框

```text
┌──────┬───────────────────────────────────────────────────────────┐
│任务  │ 我的任务   [列表 | 地图●]       范围：进行中 ▾  待处理 1 │
│文件  ├─────────────────────────────────────────┬─────────────────┤
│设备  │                                         │ 协作动态        │
│      │  研究工位                开发工位       │                 │
│      │  [桌面] 🤖 小研          🤖 小码 [桌面] │ 小研 → 白板     │
│      │  整理资料                修改页面       │ 已提交资料摘要  │
│      │                                         │                 │
│      │          ┌── 共享白板 ──┐              │ 小码 → 白板     │
│      │          │待领取 进行中  │              │ 询问接口约束    │
│      │          │需处理 已完成 │              │                 │
│      │          └─────────────┘              │ [查看原文]      │
│      │                                         │                 │
│      │  待命座位          交付架               │ 点击角色或白板  │
│      │  🤖 小审           [报告] [文件]        │ 查看详细信息    │
│      │                                         │                 │
│设置  ├─────────────────────────────────────────┴─────────────────┤
│      │ 正在工作 2 · 待命 1 · 不可用 1     [减少动态] [回到全景]  │
└──────┴───────────────────────────────────────────────────────────┘
```

线框中的角色、数量和工作内容仅用于解释布局，不代表当前运行状态。1366×900 下地图主体建议约 760×500，右侧信息栏约 300px；不要求精确照搬尺寸，优先保证文字可读和操作可达。

### 场景物件与含义

| 元素 | 表达的内容 | 点击结果 |
|---|---|---|
| 像素 Bot | 一个已配置的 Bot 身份 | 打开助手信息与正在处理的工作 |
| 工位 | 该 Bot 正在执行的工作 | 查看当前卡片；并发时先选工作项 |
| 中央共享白板 | 当前范围内卡片及其协作记录 | 信息栏切到白板摘要 |
| 白板便签 | 一张真实卡片 | 展示状态、负责人、问题、结果入口 |
| 交付架 | 有真实结果的已完成工作 | 查看结果与可用产物 |
| 待命座位 | 可用但当前未执行的 Bot | 查看能力与待命状态 |
| 灰色工位 | 停用、离线或状态未知 | 查看原因与连接诊断入口 |

工位按照稳定的 Bot ID 分配位置，刷新、状态变化不会导致整张地图重排。角色进入待命区时保留工位标记。角色名使用用户配置的名字，头像可由预设外观稳定分配；引擎名称 Pi / Codex / Claude 放在详情中，不强迫用户以引擎认识角色。

首期只做一个办公室模板。地图按任务协作组织，执行设备在角色详情中说明，不把每个 VPS 强制画成一个独立房间。

## 4. 像游戏的感觉从哪里来

- 工作时：角色坐在工位，轻微打字或翻页；显示一行真实的最新工作摘要。
- 写入白板时：短暂出现“便签 → 白板”的动效，附近浮现一句摘要。
- 开始工作时：确认领取后，角色走向工位；卡片显示负责人。
- 提问时：白板出现问号便签，角色头顶短暂出现“有个问题”；只有明确需要用户回答时，进入待处理提醒。
- 完成时：角色向交付架放下一张成果卡，出现一次轻量完成反馈；没有文件时放“结果摘要”，不伪造文件。
- 待命时：坐着或站在待命区，低频眨眼，不随机假装看文档或交流。
- 离线时：停止工作动作、降低饱和度，清楚显示“离线”或“状态待同步”。

装饰动作不表示真实行为。打字只能表示“正在执行”，不能表示某个真实键盘工具正在调用。走到白板也不表示消息刚被接收；真正的事件在旁边以文本和时间呈现。

角色动画建议 4—8 帧，基础贴图 32×32 或 48×48；整数倍缩放并关闭纹理平滑。人物、家具使用像素美术，任务正文和状态用普通清晰字体，不把整页文字做成难读的像素字。

## 5. 角色状态和多任务表达

状态分三层：**可用性、当前工作、短时事件**，不能用一个角色动画混淆这些含义。

| 真实信息 | 角色表现 | 文案与注意事项 |
|---|---|---|
| Bot 已启用、节点可用、执行数为 0 | 待命动作 | “待命”；不等于保证能匹配所有任务 |
| 当前 Attempt 正在运行，来源新鲜 | 工位工作动作 | “正在处理：卡片标题” |
| 同一 Bot 有多个正在运行的工作 | 一个角色，工位显示 ×N | 详情列出各项；不复制成 N 个独立 Bot |
| 卡片 READY | 白板待领取列出现便签 | 尚未领取，不提前让指定 Bot 工作 |
| WAITING_APPROVAL | 白板出现批准标记 | 展示具体批准对象，不能混作发送邮件授权 |
| BLOCKED | 对应工作显示受阻/提问标记 | 依据具体事件说明原因，不自动假设等待用户 |
| REVIEW | 成果便签显示“待验收” | 卡片尚未完成，不播放最终交付完成状态 |
| DONE | 一次交付动效，随后按其他工作更新角色 | 单卡完成不等于整个 Goal 完成 |
| FAILED / CANCELLED | 卡片显示失败/取消 | 保留原因，不用庆祝动作 |
| Bot 停用 / 节点离线 | 角色静止，标记不可用 | 显示最近已知信息；不能继续循环打字 |
| 数据过期或状态相互冲突 | 暂停语义动画，显示待同步 | 不自行推断任务已结束或 Bot 可接新任务 |

若 Bot 同时有一项被阻塞、一项在运行，仍在工位显示“进行中 1 · 受阻 1”；提问标记附着到对应工作项，不能把整个 Bot 变为停止。列表中的暂停等状态只有映射到真实执行对象时才展示，不给白板枚举虚构 PAUSED 状态。

## 6. 白板交流：让协作过程看得懂

白板是交流的中心。所有交流提示必须能回到原始卡片事件；地图不新建 Bot 私聊通道、不绕过 Kernel 给 Bot 发命令。

### 一段完整的示例过程

1. 用户提交“做一份竞品分析报告”。编排产生资料整理、比较分析、报告汇总等真实卡片后，白板出现便签。
2. 研究 Bot 确认领取资料卡片，角色走到工位，摘要显示“整理资料”。
3. 研究 Bot 提交结果，白板出现“资料摘要已提交”；卡片处于 REVIEW 时显示待验收，通过后才显示完成。
4. 分析 Bot 确认领取依赖工作后开始工作。依赖尚未满足时，只显示“等待资料”，不演成收到通知后已经开工。
5. 分析 Bot 在卡片写下问题或评论，白板闪现对应便签；有合法 @ 引用时可以标注接收对象。
6. 若执行链路明确向用户提问，顶栏出现待处理入口；用户打开正常任务详情回答。
7. 汇总 Bot 提交报告后，交付架出现结果。只有整体任务确实结束，任务视图才显示已完成。

### 动效语义

| 事件证据 | 可以展示 | 不可据此推断 |
|---|---|---|
| card comment / progress 已写入 | A → 白板，“新增评论/更新进度” | B 已阅读、理解或开始执行 |
| comment 包含可解析的 mentions | 白板便签上“提到 B” | 已送达、已读回执 |
| 独立回复事件，作者身份可验证 | B → 白板，“新增回复” | 无关联 ID 时断言回复了某条特定评论 |
| 成功领取及当前 Attempt 关联 | 白板 → 工位，“B 开始处理卡片” | 把依赖连线当成领取事件 |
| depends_on 关系 | 选中卡片时显示淡色依赖线 | 已实际发生消息传递 |
| 结果提交 / 审核通过 / 完成 | 分别显示提交、待验收、完成 | 把这三步合成一次成功 |

默认只显示最多 2 个短气泡，每条不超过两行，约 4 秒后收起。气泡只摘录真实事件摘要，不用 LLM 编造“我来接力啦”等对话；完整内容在动态栏和详情中阅读。截断需保留“查看原文”。事件文本按纯文本安全渲染，不执行 HTML、链接脚本或指令。

## 7. 点击与操作规则

**点击 Bot**：右栏展示名字、角色、可用性、当前工作列表、最近一次有效事件及执行设备。可“查看任务”“查看白板记录”；“配置助手”进入原设置，不在小地图上弹出复杂配置表。

**点击白板**：右栏展示当前范围的待领取、进行中、需处理、已结束卡片及数量。每组可以展开；取消与失败在已结束组中保留不同状态。场景中的微型便签不可读时，右栏必须提供完整可点击列表。

**点击气泡或动态**：定位卡片，显示作者、时间、事件种类和原文。返回地图时保留范围、选择和镜头位置。

**点击需要你处理**：进入现有任务详情或具体待处理项，查看动作范围后再批准/回答/验收。地图首期只读，不提供“点击角色就批准”“拖到工位就分配”之类隐式执行操作。

**移动地图**：支持拖动空白区域平移、工具栏缩放和“回到全景”；角色和白板点击不触发平移。滚轮默认滚动页面，缩放使用按钮或明确组合键，避免困住页面滚动。

选择任务、Bot 和事件都是查看行为，不触发模型请求、重新编排、领取或执行。

## 8. 信息优先级和规模控制

首屏优先级：需要用户处理 > 当前选中任务 > 正在工作 > 待命 > 装饰。地图再热闹也不能遮住待处理入口。

- 1—8 个 Bot：完整展示，每个角色都有清晰名字和状态。
- 9—24 个 Bot：稳定分页为办公区，每区不超过 8 个；未显示区有工作和异常数量，可一键定位。
- 超过 24 个 Bot：优先使用按任务/状态筛选及可搜索的助手名单，场景只渲染当前区；不把所有角色缩成不可点击的小点。
- 场景只显示少量便签缩略形状，完整卡片始终在右栏；数量是实际当前范围总数，不是画出来的便签数。
- Bot 名字相同使用短标识辅助区分；长名字截断且提供完整可访问名称。
- 没有 Bot 时显示空办公室与“配置助手”；有 Bot 但没工作时显示待命与“开始任务”。
- 旧会话没有可验证的 Bot 关联时，提示“此任务暂无协作地图”，保留任务详情入口；不生成虚拟参与者凑场景。

## 9. 现有数据基础与缺口

已读取的前端合同：`apps/desktop/src/lib/board.ts`、`components/NodesPanel.tsx`；架构约束参考 `docs/kernel-lite-redesign.md`。这些来源表明有可用的数据基础，不表示实时投影、回放或本功能已实现，也不替代后端合同核验。

| 当前可见合同 | 地图用途 | 实施前待核验或补齐 |
|---|---|---|
| `/api/bots`：身份、配置、running、concurrency | 角色名单和执行数量 | 数量的刷新时效、与 Attempt 的一致性 |
| `/api/topology`：节点状态、heartbeat_at、关联 Bot | 可用性和设备信息 | 心跳新鲜度规则与失联判定 |
| `/api/board`：卡片、负责人、depends_on、current_job、latest | 白板、依赖和最新进度 | 大规模分页、范围过滤、快照一致性 |
| `/api/cards/{id}`：events、runs、result | 卡片详情和事件证据 | events 截断/分页、作者身份、结果权限 |
| `/api/remote/jobs/{id}/events` | 必要时定位 Attempt 事件 | 事件排序、增量读取及状态映射 |
| 现有事件 WebSocket 与 Goal 数据 | 通知刷新、关联任务范围 | 完整事件覆盖、断线游标、Goal–Card 关联获取方式 |

特别注意：`Card.goal` 在当前前端接口中是字符串描述，不能把它当作 Goal ID。`CardEvent.actor` 也不能未经核验就当作 Bot ID。角色归属、任务关联及回复关系需要明确的标识合同。

建议增加独立的地图投影层（位置和形式待实现阶段决定），统一输出角色可用性、工作引用、待处理引用、事件引用和数据新鲜度。它不持有新的任务状态机，也不向执行器直连。

拟议的引用至少包含：连接/实例身份、Bot ID、卡片 ID、Attempt ID、源事件 ID、源时间与版本。新增的全局游标、关系字段、摘要接口如确有需要，应先定义 API 合同；涉及持久化结构时按仓库规范新增迁移。

## 10. 实时更新与动画的一致性

页面进入先读取状态快照，角色直接就位；不能把历史事件全部当成刚发生来播放。快照之后只播放确认未见过的新事件。

- 用源事件唯一标识去重。若 seq 只在卡片或 Attempt 内单调递增，必须连同所属对象 ID 使用，不当成跨工作空间全局序号。
- 连接切换时清空当前投影、事件缓存和动画队列；选中对象也按实例隔离。
- 状态刷新先更新文本与待处理数量，再调度短动画；动画积压不能拖延真实状态。
- 事件乱序时，以源对象版本与有效快照校准；旧的“开始”事件不能让已完成角色重新开始工作。
- 快照与增量缺少一致游标时，首期用通知触发重新拉取，并标注刷新时间；不宣称无损实时回放。
- 重连先重新同步，缺失事件作为“离线期间更新”列出，默认不补播大量走路动效。
- 接口失败保留最后已知画面并显示“状态待同步”和时间，停止具有工作含义的循环动作；不通过本地超时把任务设为完成。
- 事件突发时合并相同对象的展示队列，优先保留问题、失败和完成；动态栏保留可追踪记录，不因少播动画丢掉业务信息。

仅打开当前范围和选中卡片的必要详情，避免每个 Bot、每张卡分别无限轮询；后台标签页暂停动画并降低刷新负载，重新可见时先同步。

## 11. 动效、可访问性与隐私

- 默认无音效；首期不加入背景音乐，完成反馈不使用强闪烁。
- 提供“减少动态”，并尊重系统 `prefers-reduced-motion`；关闭走路、气泡飘动和循环打字后，信息仍完整。
- 角色和白板配有语义化 DOM 操作入口；即便场景最终采用 Canvas，也不能只靠画布坐标完成任务。
- 键盘可选择助手、阅读动态和进入任务；屏幕阅读器使用等价列表。实时播报只提示重要变化，避免每次动画都打断阅读。
- 小于 900px 时右栏改为场景下方详情；窄屏可优先提供助手列表，不要求缩到无法辨认的办公室。
- 在地图上隐藏敏感正文、文件绝对路径、工具参数和凭据；默认气泡只显示简短业务摘要。提供“隐藏工作内容”开关，用于演示或屏幕共享。
- 权限继承原工作空间及对象访问规则。地图不能因汇总事件而展示当前用户无权查看的结果。

## 12. 首期范围与后续选项

### 首期必须有

1. 任务页“列表 / 地图”切换，复用筛选与待处理入口。
2. 一个像素办公室、稳定 Bot 身份、真实可用性和当前工作摘要。
3. 白板中心、基本的领卡/写入/提问/交付反馈，能追溯原始事件。
4. Bot、白板、事件的详情侧栏与原任务跳转。
5. 多任务、多 Bot、空态、断线、减少动态及等价列表。
6. 明确展示模式：真实数据或带明显标识的演示数据，二者不能混用。

### 首期不做

地图拖拽派活、实时 Bot 私聊、自由建造办公室、虚拟经济、角色成长、排行榜、跨 Kernel 合并、历史事件动画回放、拟人化自动对白。也不在本次文档阶段制作角色贴图或实现地图。

### 后续可以考虑

- 用户为 Bot 选择外观、工位配色和办公室主题，仅作为展示偏好。
- 数据合同支持后，增加带时间范围和“回放中”标识的协作回放。
- 更大团队的多房间导航，但必须保留跨房间待处理汇总。
- 明确授权与版本校验完备后，再讨论拖拽分配；不能直接复用视觉拖动作为执行指令。

## 13. 建议实施分段

**A：确认语义与数据。** 对齐 Bot 可用性、卡片状态、任务关联、事件作者及待处理来源，形成投影合同与固定示例场景。

**B：做静态可访问视图。** 实现列表/地图切换、办公室、角色标签和详情跳转；先保证每个图形都有准确解释，不依赖动画表达关键信息。

**C：接入真实更新与轻动效。** 用同一投影驱动画面和文本，实现去重、断线同步、多任务和事件合并。

**D：性能与实机验收。** 覆盖 Windows Tauri 实际环境、多个执行引擎和离线恢复；通过后再考虑外观定制。

建议使用现有 React 管理布局和语义控件，像素精灵使用 CSS 或独立轻量画布层；不默认引入完整游戏引擎。具体技术选型以角色数量、资源体积和 Tauri 实测为准。

## 14. 验收标准

以下为未来实现的验收目标，本次未执行功能测试。

| 场景 | 通过条件 |
|---|---|
| 3 个 Bot 协作同一任务 | 能看清各自工作和白板记录，点击到达正确卡片 |
| A 评论并 @B，B 尚未响应 | 只显示已发布和提及，不显示已读或开工 |
| 同一 Bot 并发两项，一项阻塞 | 显示 1 个角色及两项真实状态，不整体误报停工 |
| 卡片提交后待验收 | 显示待验收，不提前标完成或展示最终庆祝 |
| 节点离线但卡片仍 RUNNING | 显示离线与最后已知状态，不继续打字或擅自改卡片状态 |
| 相同事件重复/乱序到达 | 动效最多播放一次，终态不会倒退 |
| 断线后恢复 | 同步后显示当前状态，不补播整个历史，不重复审批提醒 |
| 切换 Kernel | 旧角色、事件和动画立即隔离，不跨连接展示 |
| 无 Bot / 无任务 / 无协作关联 | 有明确说明与合适入口，不伪造活动 |
| 24 个 Bot、100 张卡片 | 分区和筛选可用；100 条事件/秒的模拟突发合并后界面仍可操作 |
| 减少动态和键盘使用 | 不看动画也能完成查进度、找问题、看结果 |
| 地图操作的副作用 | 查看、移动镜头、选择对象均不触发执行或模型请求 |

性能目标：标准窗口中当前区最多 8 个角色，动画按约 30fps 设计；重要业务事件在前端收到后 1 秒内更新文字/提示，场景动效可合并延后。具体 CPU/GPU 和内存预算需基于 Windows 实机记录，不以开发机观感代替验收。

可用性目标：不熟悉系统的用户能在 10 秒内指出“谁在工作、哪里卡住、下一步该点哪里”。通过用户测试验证，不把这个目标当作已达成的结论。

已做到：

- 只读：查看地图不产生任何写入；卡片详情复用 `CardDetailView` 的 `readOnly` 模式，不显示批准、验收、取消和评论。

第二轮评审修复（2026-10-30）：

- 白板数据合同新增 `recent_events`（含评论、回答与 `mentions`，带后端事件 ID）和 `last_job`（最近一次 Attempt）。协作动态与气泡按 `卡片ID#事件ID` 去重，评论和 @提及现在能显示；`latest` 语义不变。

- 没有实时回放；只对轮询到的最新动态做一次性提示。
- 角色外观是按 Bot ID 着色的像素小人，不代表引擎或状态。

## 入口与助手名册（2026-10-30）

反馈“地图做了但页面上没马上看到”：地图原先只是任务列表旁一个不起眼的切换项。现在任务首页在输入框下方常驻“助手”名册（`components/BotRoster.tsx`），右侧有“打开工作地图”按钮，点击切到地图视图并滚动到位。默认视图仍是列表，因为已结束任务的删除按钮在列表里。

名册与地图共用同一份投影（`projectWorkMap`），状态不另行推断：工作中 / 待命 / 不可用 / 状态未知，并发时显示 ×N；数据过期或设备信息未读到时同样降级为“状态未知”。点击助手把 `@名字` 写进输入框。

在输入框里输入 `@` 会弹出已启用助手的候选（↑↓ 选择，Enter/Tab 确认，Esc 关闭）。提交时文本里提到的、确实存在的助手名随 `POST /api/goals` 的 `bots` 发送，编排器优先分派给它们；会话直连路径不支持指定助手，页面会提示 @ 被忽略。尚未在真实多 Bot 环境中验收。

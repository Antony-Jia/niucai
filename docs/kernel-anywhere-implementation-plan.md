# Kernel 任意位置部署与多 Bot 协作落地计划

日期：2026-10-13  
状态：已落地核心代码并完成本地协议/协作验证；真实 VPS、真实模型、Windows 原生安装与跨主机迁移现场验收未完成。详见 `kernel-anywhere-contract.md`、`kernel-anywhere-operations.md` 和 `kernel-anywhere-validation-20261013.md`。本文后续“待实现”措辞保留为原计划的设计记录，当前实现以合同与验收记录为准。  
第一期目标：Windows Desktop 与 Kernel 可在同一台电脑运行，统一接入本地 Docker 和可达 VPS，完成一次主任务调配多个预配置 Bot 的真实闭环。

## 1. 核心决策

1. Kernel 的部署位置不决定资源的位置。Kernel 可以在用户电脑、局域网服务器或 VPS；第一期首先交付 Windows Desktop + 同机 Docker 内的 Kernel。
2. 一个控制中心包含 API、PostgreSQL、主 Worker、Pi 会话和产物存储。第一期主 Worker 与持久卷同机，不扩展为多主机 Worker 集群。
3. Desktop 是管理界面。关闭界面不停止 Kernel/Runner；电脑休眠、关机或 Docker 停止会影响同机服务，界面必须明确显示此限制。
4. Node Runner 主动连接 Kernel，领取工作、维持心跳并回传。沿用现有协议，不要求 Kernel 直接控制远端 Docker daemon。
5. Bot 是持久身份与策略，Node 是执行位置，Computer 是可交互设备，三者不能互相替代。
6. 一次用户主任务对应一个 Workflow，由 main 协调多个 WorkItem；每个 WorkItem 有明确 Bot 负责人，底层沿用 Task/TaskRun/Remote Job。
7. Bot 的身份、角色、模型角色映射、工具、资源绑定和交付约定一次保存。运行时创建配置快照，main 无权越过该配置扩大权限。

## 2. 部署与网络合同

### 2.1 第一期默认拓扑

```text
用户电脑
  Windows Desktop ── localhost 管理入口 ──┐
  Docker Desktop（Linux）                │
    Kernel API + PostgreSQL ◄────────────┘
    主 Worker + Pi Runtime
    本地 Node Runner ── Compose 内网 ──► Kernel API
    独立持久卷：数据库 / Pi 会话 / workspace / 节点数据

远程 VPS
  Node Runner ── 可达的受保护地址 ──► 本机 Kernel API
                 （跨网络通道须先建立）
```

Kernel 移至 VPS 时协议不变：Desktop 和本地 Runner 都改为连接 VPS Kernel 地址。迁移包含状态与凭据迁移，不能仅修改 URL 就宣称原任务已迁移。

### 2.2 “可连接资源”的准确定义

用户关注的是资源能否被调度；当前协议实际要求 **Runner 能访问 Kernel**。Kernel 能 SSH 到 VPS，并不自动证明 VPS 能回连 Kernel。

| Kernel 位置 | Runner 位置 | 第一期开通方式 | 地址说明 |
|---|---|---|---|
| 本机 Docker | 同一 Compose 网络 | 内网服务名 | 例如容器内的 `http://api:8080`，不是 Desktop 地址 |
| 本机 Docker | 本机独立 Docker 网络 | 显式加入受管网络，或配置可达宿主机入口 | 不默认假设 `host.docker.internal` 能访问回环绑定端口 |
| 本机 | 远程 VPS | 已配置的私有网络，或受保护的反向隧道/HTTPS 入口 | 默认 `127.0.0.1:8080` 无法被 VPS 访问 |
| VPS | 本地 Docker / 其他 VPS | Runner 访问 Kernel 的 HTTPS 地址 | 本地 Runner 不需要开放入站端口 |
| 任意 | 无任何可达通道 | 不准入执行 | 明确提示缺少连接通道，不显示“配置成功”代替在线 |

第一期交付一种可复现的“本机 Kernel → VPS Runner”网络路径：通过用户指定的 VPS SSH 连接建立反向隧道，VPS 端仅监听回环；VPS Runner 通过专用转发容器共享网络命名空间访问该回环端口。隧道目标指向本机 Kernel 回环入口，不公开 VPS 转发端口。Linux 专用 VPS 可提供 host-network 备选说明，但不能默认要求所有节点使用 host network。

实施前先完成小型连通性验证，固定端口映射、容器命名空间、SSH 主机密钥校验、凭据保存和断线重连方式。第一期至少交付可重复运行的启动/诊断脚本；Desktop 自动维护隧道可在同一期后段接入。若现场禁止 SSH 转发，选择已配置私网或 HTTPS 入口，并记录前置条件，不承诺任意网络无配置直连。

现有 VPS 向导强制 HTTPS。若接入上述 SSH 保护的回环 HTTP，应新增明确的连接模式与相应校验，不能简单移除 HTTPS 校验。非回环公网连接继续要求 HTTPS。

### 2.3 地址与身份

分别保存 Desktop 管理地址、Runner 连接地址、连接模式。不得根据“本地 Docker”分类直接推断 Kernel 在本机。跨机器诊断必须从 Runner 所在环境发起。

新增持久 `kernel_instance_id` 和协议版本信息；Desktop 配置、节点登记、缓存和凭据以该身份隔离。迁移恢复可保留原实例身份；新建独立控制中心生成新身份，避免把多个数据库当作同一控制中心。

## 4. 领域模型与配置

### 4.1 保持现有层级

```text
KernelInstance
  ├─ BotDefinition（身份 / 角色 / 模型映射 / 权限 / 资源策略）
  ├─ ResourceNode（能力 / 在线状态 / 容量 / 调度状态）
  ├─ Computer（浏览器或桌面设备；不等同于 Node）
  └─ Workflow（主目标 / owner=main / 预算 / 最终交付）
       └─ WorkItem（负责 Bot / 输入 / 验收要求 / 配置快照）
            └─ Task / TaskRun
                 └─ Remote Job（节点工作包及 attempt）
```

第一期 Bot 的协调推理仍在中央 Worker；需要节点执行时调用受控远程工作包。资源绑定不表示整个 Bot Runtime 已迁移到该节点。节点 Pi 模型仍可与中央 Bot 模型不同，界面分别标示；不在本期暗中统一凭据转发。

### 4.2 Bot 配置合同（新增部分待实现）

| 项目 | 保存内容 | 执行规则 |
|---|---|---|
| 身份与角色 | id/name/description/instructions | 角色描述进入上下文，权限另行校验 |
| 模型 | 沿用 model_roles，显示解析后的中央模型 | 节点模型在节点详情单独展示 |
| 工具 | tools 白名单 | 保留服务端强制检查 |
| 节点范围 | 沿用 allowed_nodes | 空列表无节点权限；null 的既有含义保持兼容 |
| 选择策略 | 新增 fixed / pool；固定节点或允许集合 | fixed 不自动切换；pool 仅在授权集合内选择 |
| 工作环境 | 受管 workspace 配置、镜像/能力要求、凭据引用 | 第一期开启容器内工作区；宿主机目录必须显式选择 |
| 调度 | max_concurrency、忙时排队、离线等待上限 | 排队不占 Worker 槽位；到期给出可恢复原因 |
| 交付 | 文本、文件、测试报告等 output_contract | 结果缺失时不直接宣告主任务成功 |
| 版本 | definition_version + 工作项配置快照 | 编辑影响新工作项，已有执行不静默换资源 |

“固定绑定”与“独占”分开：固定绑定限定运行位置；执行租约控制实际占用。第一期每节点沿用一个执行槽，专属 Bot 需要专用节点容器；暂不新增可被误解为文件安全隔离的软独占选项。

配置快照不能阻止紧急撤权：禁用 Bot/节点、收紧权限和全局停止仍在派发与执行边界重新检查。策略变化导致权限不足时停止新动作并展示原因，不能继续使用旧快照绕过撤权。

### 4.3 一次配置的用户流程

1. 选择“本机控制中心”或“连接已有控制中心”。
2. 添加资源：本地 Docker 或 VPS；独立选择连接模式并完成真实上线验证。
3. 创建 Bot：填写职责、模型映射、工具、绑定资源、工作环境和交付要求。
4. 保存时校验资源存在、权限一致、模型角色可解析；离线资源允许保存为“待验证”，不能标成可执行。
5. 创建主任务，选择可参与 Bot 和交付目标；main 查看结构化 Bot 目录后分工。
6. 主任务页显示负责人、各工作项、实际节点、等待原因、产物及最终汇总。

## 5. 实施工作包

每个工作包单独提交可评审变更与验收记录。依赖顺序：P0 → P1 → P2 → P3 → P4 → P5；P2 的网络验证应尽早进行，避免最后才发现现场不可达。

### P0：冻结合同与基线（1–2 人日）

- 负责人角色：架构/后端。
- 核对当前未提交工作、迁移 head、功能开关、现有测试和部署入口，保存基线记录，不覆盖其他改动。
- 固化本文件的领域、连接模式、Bot 资源策略和等待原因；补充 API 合同草案与兼容矩阵。
- 对现有多 Bot 文档的历史基线与最新实现状态做标识，避免“未实现”和“已实现”混用。
- 交付：合同文档、迁移清单、验收用例清单、网络验证方案。
- 退出条件：同机与跨网络地址流向明确；fixed/pool、撤权、离线和审批行为无歧义。

### P1：同机 Kernel 产品化（3–4 人日）

- 负责人角色：部署/Desktop。
- 范围：`deploy/compose/`、启动脚本、`apps/desktop/src-tauri/`、Settings。
- 建立受管 Compose 项目和独立持久卷；Windows 上 Kernel Worker 在 Linux 容器运行。
- Desktop 提供 Docker 状态、安装/启动/停止 Kernel、健康检查和日志入口。只管理带本应用标识的项目，不操作其他容器。
- 固定本地端口并检测冲突；凭据在本地安全存储，不写前端缓存或日志。
- 健康诊断分别报告 API、数据库迁移、Worker 心跳、模型配置；API 200 不等于执行就绪。
- 交付：本机启动闭环、实例身份接口、健康诊断、保留数据的重建流程。
- 退出条件：全新环境可启动并完成纯推理任务；关闭/重开 Desktop 历史保留；重启受管容器后可继续使用。

### P2：资源接入与跨网络闭环（4–6 人日）

- 负责人角色：Runner/部署/Desktop。
- 范围：ResourceManager、resource-package、Tauri 受管命令、Runner、远程节点 API。
- 本地自动部署 Runner 至受管网络，避免手输宿主机地址；保留手动包供高级用户使用。
- VPS 提供固定版本安装包或可用的固定版本镜像；在镜像发布链未就绪时明确使用源码构建，不依赖不存在的镜像。
- 实现 2.2 中一种跨网络路径，交付 SSH 隧道脚本和日志诊断；身份验证使用系统 SSH/key agent 或私有凭据引用。
- 区分“Docker 未启动、隧道断开、地址不可达、token 无效、协议不兼容、Pi 未就绪、模型调用失败”。
- 节点配置接口增加连接模式和能力/协议版本；节点 token 不具备控制中心管理权限。
- 交付：同机 Kernel + 本地 Runner + 真实 VPS Runner 的实测记录。
- 退出条件：两节点均完成真实工作包；从 Runner 环境验证可达；断开隧道可检测，恢复后旧任务按现有核对规则处理。

### P3：Bot 一次配置与强制资源绑定（3–5 人日）

- 负责人角色：后端/Desktop。
- 范围：AgentDefinition、bots API、remote 调度、Bots 页面、Context Compiler。
- 增加上述配置合同、版本、引用校验和工作项快照；完整展示现有字段。
- main 获取结构化 Bot 目录，包含职责、允许的委派对象、资源就绪情况和交付要求；不提供原始凭据。
- fixed 只派发到指定节点，pool 仅从授权集合调度；节点忙/离线可见，禁止静默回退到中央 Shell。
- 工作包必须实际包含所需角色规则、受控输入及交付合同；不能只在中央提示词中保存角色而让节点执行丢失上下文。
- 保留远程工作包现有人工审批。一次配置不自动等于永久批准所有后续外部动作。
- 退出条件：配置开发 Bot 固定本地节点、验证 Bot 固定 VPS；重开客户端配置仍有效；越权指定其他节点被服务端拒绝。

### P4：主任务协作与产物交付（4–6 人日）

- 负责人角色：协作后端/Runner/Desktop。
- 范围：collaboration、pi_adapter、artifacts、Runner、Chat/Workbench。
- 复用 Workflow/WorkItem 展示主任务；main 并行委派、等待汇总或阶段转交，各工作项有独立执行会话。
- 复用现有 Artifact 元数据补二进制上传/下载：第一期默认单文件 20 MiB、每工作项 100 MiB，服务端可配置；流式传输、校验和、幂等 finalize、未完成上传清理。
- Artifact 访问校验工作流与工作项范围；节点只能上传/下载其被授权工作包相关文件，文件名与解压路径校验在节点执行。
- 交付以受控产物引用流转，不假设两台机器共享路径。第一期覆盖源文件/测试报告，自动 Git 合并与冲突处理后续单独设计。
- 主任务汇总显示部分失败，不把单个 Bot 完成当作整个目标完成；需要人工审批时定位到实际工作项。
- 退出条件：main → 开发 Bot（本地）→ 文件产物 → 验证 Bot（VPS）→ main 汇总闭环成功；另测两个独立工作项并行推进。

### P5：恢复、迁移与发布验收（3–5 人日）

- 负责人角色：测试/后端/部署。
- 使用独立 PostgreSQL 测试环境，覆盖真实行锁、多槽位、等待释放和取消竞争。
- 故障注入：关闭 Desktop、停止 Worker、断隧道、重启 Runner、Kernel 停机、旧 attempt 迟到回传、重复提交。
- 保留 LOST 占用与退出核对语义；不能因心跳过期就自动把可能执行过副作用的工作转派到另一节点。
- 演练本机 Kernel 迁至 VPS：停止新准入、结束或核对在途工作、停止写入、备份数据库/Pi/Artifact/workspace、恢复到目标、更新地址与节点配置、验证后启用。
- 原实例不得与恢复实例同时调度；回滚也必须避免双活。已迁移数据库不通过破坏性 downgrade 回退。
- 交付：部署手册、故障矩阵、备份恢复记录、验收证据和版本兼容说明。
- 退出条件：下面所有一期必过场景完成，已知限制明确记录。

工作量初估为 18–28 人日，不是日历承诺；按每阶段出口修订，网络接入条件与产物传输是主要不确定项。

## 6. 一期验收矩阵

| 编号 | 场景 | 必须看到的证据 |
|---|---|---|
| A1 | Desktop + Kernel 同一 Windows 电脑 | Linux 容器运行、鉴权健康、Worker 就绪、真实任务结果 |
| A2 | 本机 Kernel 调度本地 Docker | 节点心跳、Job/attempt ID、实际节点 ID、文件结果 |
| A3 | 本机 Kernel 调度不同网络的 VPS | 通道配置、VPS 内连通性、真实模型工作包与产物 |
| A4 | VPS Kernel 调度本地 Runner | 更换拓扑仍使用同一 Runner 协议，完成实际工作包 |
| A5 | Bot 配置一次后重复使用 | 两次主任务保持角色与固定资源，配置版本可追溯 |
| A6 | 多 Bot 并发及串行交接 | Workflow/Handoff/Task/Job 关联，等待不占槽、产物哈希一致 |
| A7 | 固定节点忙或离线 | 显示排队或离线原因，不在未授权节点执行 |
| A8 | 审批和撤权 | 未批准工作不执行；执行前收紧权限可阻止新动作 |
| A9 | 中断与恢复 | 无重复工作项；旧 attempt 拒绝；LOST 未核对不自动释放 |
| A10 | 关闭 Desktop | 同机 Kernel/Runner 继续执行，重开可恢复查看 |
| A11 | Kernel 迁移与回滚演练 | 历史与产物可读、会话存储完整、旧实例停止调度 |
| A12 | 文件跨节点与访问边界 | 正常下载、越界访问拒绝、校验失败拒绝、限额生效 |

确定性模型用于协议/恢复测试，真实模型用于协作质量与实际执行验证，两类证据分开保存。每次验收记录版本、拓扑、开关、节点与任务 ID、结果和限制；不保存 token、模型密钥或 SSH 私钥。

## 7. 兼容与上线方式

- 不迁移成另一套任务引擎；沿用现有数据库实体与幂等/租约协议，使用前向 Alembic revision。
- 老 Bot 默认保持既有 allowed_nodes 行为，新建 Bot 默认无节点权限，要求显式配置；不静默改变 main 的既有策略。
- 旧节点标记为未验证版本/能力，完成探测后再启用新增能力，基础工作包维持兼容路径。
- 新连接模式与新配置独立灰度；多 Bot/远程执行开关继续可诊断，关闭前处理已有协作执行。
- 备份不仅是数据库，还包括 Pi 会话、工作区和产物；节点本地数据另行备份。控制中心迁移不自动迁移节点工作区。
- 节点容器启动与任务执行权限分离；模型工作包不直接获得宿主机 Docker socket。未来需要管理其他容器时，另加受限执行接口。

## 8. 一期范围之外

- 每个 Bot 的完整长期推理会话都在绑定节点运行的分布式 Runtime。
- 多主机中央 Worker、高可用控制中心和双活数据库。
- 任意网络自动穿透、无用户配置的云中继服务。
- 全功能远程桌面/浏览器跨节点代理；现有 Computer 接口保留，不能把 Runner 上线当作桌面可交互。
- 自动合并多个 Bot 修改的同一代码库、宿主机所有目录/容器的默认访问权限。
- 多用户团队权限和每个工作项独立的强隔离沙箱。

一期完成标准：用户在自己的电脑启动控制中心，接入一个本地 Docker 节点和一个真实 VPS 节点，一次配置两个 Bot，再通过一个主任务完成分工、执行、文件交接和汇总；同一套协议支持将控制中心改部署到 VPS。

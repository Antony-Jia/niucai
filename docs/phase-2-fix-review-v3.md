## 恢复幂等性仍是错误场景，不能升级为通过

关键日志：records/sideeffect-resume-stage1-20261008T035427Z.log 及 sideeffect-resume-stage2-20261008T035822Z.log。

源任务在备份前已经 COMPLETED，四条动作均 SUCCEEDED。恢复后还是 COMPLETED，resume 返回 409，任务根本没有进入恢复执行路径。这证明完成记录、文件内容恢复及终态恢复拦截正常；不证明非终态任务恢复执行时不会重复派发先前成功动作。

脚本头部设计原本是“第一次写成功后，停在第二次审批”，但实现的 stage1 自动批准后续审批并等待任务 COMPLETED，与设计相反。

此外文件内容相同不是此处的派发计数证据：当前 LocalAdapter 的 files.write 调用 Path.write_text，是覆盖写入。再次执行相同写入，最后仍可能得到完全相同的两行。三份文件本机比对均为 23 字节且完全一致，只能接受为文件恢复与终态保护的证据。

## 给 Hermes 的精确补验要求

只补这一条恢复测试，不必重做已通过的包校验、JUnit 和隔离浏览器验收：

1. 创建同一任务的两次写入流程，只批准第一次写入。
2. 当第一条写动作为 SUCCEEDED，且任务停在第二条写动作的 WAITING_APPROVAL 时，立即停止 stage1。**不得批准第二次写入，不得等待 COMPLETED。**
3. 增加硬断言：备份时任务必须非终态，至少一条动作 SUCCEEDED，并存在一条尚未批准的写动作；否则演练直接失败。
4. 备份恢复到独立环境，检查第一条成功动作及同一 Pi 会话仍在，批准第二次写入，让原任务实际推进到完成。
5. 用隔离环境的适配器派发计数/日志验证：第一条写动作从源栈到恢复栈合计只派发一次，第二条在恢复后只派发一次。配合校验原动作 ID、幂等键、已成功状态及预期的新动作。
6. 若暂时没有实际派发计数，只能继续标为部分通过，不能用最终文件相同或动作行不变代替。

以上流程可利用现有 files.write 审批，无需新工具或开放 shell，也不依赖生产浏览器。
